Decision 2:
Date: 2026-05-31
Context: Choosing between opencv-python and opencv-python-headless for requirements.txt.
Decision: Chose opencv-python-headless over opencv-python.
Rationale: opencv-python bundles Qt GUI libraries (~200MB larger) that are not needed
  in a headless server/Docker environment. opencv-python-headless has no display
  dependency, installs faster, produces a smaller Docker image, and avoids X11
  errors inside containers that have no display server.
Trade-off: Cannot use cv2.imshow() or any GUI windows. All visualisation during
  development must use file output (cv2.imwrite) or separate tooling.
CHOICES.md section: Dependency Choices

Decision 3:
Date: 2026-05-31
Context: zones.json polygon coordinates are required before the detection pipeline
  can run, but video files have not yet been inspected.
Decision: zones.json created as a template with empty polygon arrays and TODO markers.
  Coordinates must NOT be invented or fabricated. They must be derived from:
  (a) Brigade_Road_Store_layout.xlsx inspection, and/or
  (b) Frame extraction from actual video files using visualise_zones.py.
Rationale: Fabricated coordinates would produce silently wrong zone classifications
  that inflate or deflate all funnel metrics without any error signal. An empty
  template with clear TODO markers fails loudly (zone_classifier.py will warn),
  which is safer and more honest than fake data.
Trade-off: Pipeline cannot run until Phase 2 zone extraction is complete.

Decision 4:
Date: 2026-05-31
Context: CAM 4 covers the warehouse/storage zone. Choosing between YOLOv8 person
  detection and OpenCV background subtraction.
Decision: CAM 4 uses background subtraction (OpenCV MOG2) rather than YOLO.
Rationale: The warehouse zone requires activity detection, not customer identification.
  Background subtraction is faster, lighter, and more appropriate for the task.
  A minimum contour area threshold (500 sq px at 640x360, configurable via
  warehouse_motion_threshold in config.json) filters lighting-induced false
  positives, retaining only motion events consistent with human presence.
  No YOLO model weights are needed for this camera.
Trade-off: Cannot count individual people in the warehouse. Returns motion events
  and restocking duration estimates, not headcounts.
CHOICES.md section: Detection Strategy — CAM 4

Decision 5:
Date: 2026-05-31
Context: Choosing a person tracking strategy across all cameras.
Decision: Implement a lightweight centroid tracker as the primary tracker.
  ByteTrack is a documented fallback, contingent on Phase 2 validation.
Rationale: Centroid tracker has zero external dependency chain. ByteTrack has
  installation friction on CPU-only environments (requires specific scipy, lap/lapjv
  versions, sometimes Cython compilation) and may produce garbage track IDs inside
  Docker without a clean dependency chain. For zone-level aggregate analytics,
  centroid tracking with configurable distance threshold (80px at 640x360) is
  sufficient and reliable.
Trade-off: Less sophisticated re-identification than ByteTrack. Occasional ID
  reassignment after occlusion is corrected by the dwell merge rule in
  session_manager.py.
CHOICES.md section: Tracking Strategy

Decision 8:
Date: 2026-05-31
Context: Brigade_Road_Store_layout.xlsx was opened and inspected to determine
  whether machine-readable zone coordinates exist for direct use in zones.json.
Decision: The Excel file contains a floorplan image only. No coordinate tables,
  no vector layers, no numeric zone boundaries. Polygon extraction must come
  entirely from video frame inspection using visualise_zones.py.
Rationale: There is no shortcut. Every polygon coordinate must be derived by
  visually inspecting actual video frames and manually placing polygon points
  in pixel space at 640x360 resolution. This is the correct approach — the only
  source of ground truth for pixel-space polygons is the video feed itself.
  Store layout knowledge (entry door on left wall, billing counter on right,
  skincare top wall, makeup bottom wall, F.O.H island center floor) informs
  where to look in each video frame, but does not substitute for coordinate extraction.
Trade-off: Time cost of manual polygon extraction. visualise_zones.py is the
  tool that will make this iterative process efficient.

Decision 9:
Date: 2026-05-31
Context: CAM 4 (warehouse) video inspection revealed visible lighting flicker.
  The default warehouse_motion_threshold of 500 sq px (config.json) was set
  before observing this flicker. Risk: false positive motion events from flicker.
Decision: Do not change the default threshold value yet. Instead:
  (a) The default of 500 sq px remains in config.json as the starting point.
  (b) Phase 2 calibration is REQUIRED for this camera specifically.
  (c) If flicker produces contours > 500 sq px, the threshold must be raised.
      Expected calibration range: 500–2000 sq px depending on observed flicker area.
  (d) Calibration method: run background_motion.py on 100 frames of CAM 4 with
      no humans present (or confirmed quiet periods), log all contour areas
      observed, set threshold above the maximum flicker-only contour area.
Rationale: Hardcoding a higher threshold now without data would be guessing.
  Keeping 500 as default while documenting the calibration requirement is more
  honest and auditable. The flicker risk is known and mitigation is planned.
Trade-off: Phase 2 must not skip CAM 4 calibration. If it is skipped, warehouse
  events will include false positives and operational intelligence will be unreliable.

Decision 12:
Date: 2026-06-01
Context: Phase 2 CV Validation begins. Structured as 5 sequential checkpoints,
  each with a dedicated validation tool in tools/. Each checkpoint stops for
  human review before the next begins.
Decision: Phase 2 is broken into checkpoints 2.1–2.5, not run as a single script.
  Checkpoint 2.1 (YOLOv8-nano smoke test on CAM_1) is the first gate — if YOLO
  cannot detect people in the actual videos at 640×360, nothing else in the
  pipeline is worth building. Results are recorded in PHASE2_REPORT.md after
  each run.
Rationale: Incremental validation with human review at each gate prevents
  building detection, tracking, and crossing logic on top of an unvalidated
  foundation. Each checkpoint produces a concrete YES/NO answer and evidence
  (annotated images or printed metrics).
Trade-off: Slightly slower than running all validation in one script, but each
  result is reviewed and recorded before proceeding.

Date: 2026-06-01
Context: Checkpoint 2.1 — YOLOv8-nano smoke test run on CAM_1.mp4 at 640×360.

    Frame 100: 2 persons, confidence 0.76–0.88

  confidence_threshold=0.5 retained. Minimum observed confidence (0.76) is
  26pp above the threshold, providing substantial headroom before false
  negatives become a risk. No need to lower the threshold.
  Consistent 2 persons detected across all 3 test frames on CAM_1 (skincare
  zone) — no frame-to-frame drop-outs observed on this camera.
Rationale: Confidence range 0.76–0.88 is strong for a retail indoor scene.
  The model generalises well to this store's lighting and camera quality
  without any fine-tuning. The 0.5 threshold is neither too aggressive
  (missing real persons) nor too permissive (admitting false positives).
Trade-off: Only CAM_1 was tested in this checkpoint. CAM_3, CAM_2, and CAM_5
  will be validated in subsequent checkpoints. It is possible that other
  cameras with different angles or lighting produce lower confidence scores.
